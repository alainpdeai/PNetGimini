# EVE_IAC_INTEGRATION_SPEC.md 修改建议(汇总版)

**评审对象**:`docs/EVE_IAC_INTEGRATION_SPEC.md`(v1.2.0)
**评审依据**:仅基于文档文本本身,以及多份独立评审意见的合并去重。未对照代码仓库,也未核实 EVE IaC 官方 API 细节。

---

## 0. 总体结论

文档的**架构方向是对的**:Git / EVE IaC / EVE-NG / PNetGimini 四层职责划分清晰,`automation_profile` 取代主机名推断,`wait_console` 语义限定,混沌操作的临时性语义,Tier 2 明确标注为"设计意图"。这些应当保留。

主要问题集中在:**它目前更像"设计意图说明",而不是"可直接指导实现的契约"**。具体缺口是状态定义、schema 版本化、回滚安全性、并发模型、审计产物格式,以及若干示例内部的不一致。

## 1. 动手改文档前,先在代码里核实的事项

以下几点只能通过读代码或跑测试确认,结论会决定后面哪些建议是"改文档"、哪些是"改实现":

| # | 待核实项 | 为什么重要 |
|---|---|---|
| V1 | `ConfigDiffEngine` 如何处理"修改值"类变更(如改 IP、改 OSPF cost) | 取反命令(`no ...`)无法恢复旧值,见 P1-1 |

| V4 | 混沌测试中途异常退出时,链路是否一定被恢复 | 见 P0-3 |
| V5 | 健康门断言是一次性检查还是带超时的轮询 | 见 P1-3 |

## 2. 修改建议清单

### P0:契约一致性与安全(必须修)

#### P0-1 补充节点生命周期状态机

**问题**:文档反复提到"OOB SSH 建立"、"冷启动就绪"、"事件探针",但没有统一的状态定义,实现者容易在"console 已有提示符但 OOB 尚未就绪"这类竞态上出错。

**建议**:
- 新增状态机,例如 `allocated → booting → console_ready → oob_ready → configurable → verified → converged`。
- 为每个状态写明:进入/退出条件、超时、重试策略、该状态下允许调用的 EVE IaC 原语。
- `wait_console` 的 `timeout_ms` 上限为 600,000 ms,建议按镜像类型给出推荐超时表。

#### P0-2 消除 YAML 示例与 API 契约的不一致

**问题**:
- `chaos_tests[].target_link` 使用人类可读主机名(`Spine-01:e0/1 <-> Leaf-01:e0/1`),而 §3.4 的 API 使用稳定节点键(`n_1`)。这与文档自己"不通过主机名推断"的原则矛盾。
- 示例配置用 `GigabitEthernet0/1`,混沌接口用 `e0/1`,命名体系不一致。
- chaos 测试写在单个节点(`Spine-01`)名下,但它描述的是涉及两个节点的链路。
- **路线图与正文矛盾**:§3.1 明确说明 `list_project_consoles` 仅作诊断用途,PNetGimini 不依赖它做主路径。但路线图 v3.2 一行把它列为核心 API 契约并写着"自动厂商驱动检测"——这与 `automation_profile` 的设计直接矛盾。该条目的描述需要同步修正。

**建议**:
- 明确一条解析规则:谁负责把显示名映射到稳定键、在哪个阶段解析、解析失败怎么办。
- 统一接口命名,或说明"IaC 层接口名"与"设备内接口名"的映射来源。
- chaos 测试提升到顶层(与节点同级),而不是挂在某个节点下。
- 路线图 v3.2 行的 API 契约列改为 `oob start / inventory generate / wait_console`(主路径),并注明 `list_project_consoles` 已降为诊断辅助;"自动厂商驱动检测"改为"基于 `automation_profile` 的驱动绑定"。

#### P0-3 混沌测试的恢复保证

**问题**:若 PNetGimini 在 `suspended=True` 期间崩溃或被终止,链路会一直保持挂起,污染后续流水线。

**建议**:
- 在文档中把"必须恢复"写成硬性要求:所有混沌动作用 try/finally(Python 里可封装为上下文管理器)包裹。
- 评估是否让 EVE IaC 侧支持 TTL 式自动恢复(租约到期自动 un-suspend),作为进程被杀死时的兜底。
- 在 Python 实现中,可考虑用 `contextlib.asynccontextmanager` 封装 `link_suspended(...)`,并在入口处增加"启动时清理残留 suspended 链路"的步骤。

### P1:正确性与可执行性

#### P1-1 重新论证 Tier 1 回滚的安全性

**问题**:
1. 取反命令不能恢复旧值。例如把 IP 从 A 改为 B,`no ip address` 只会删除 B,并不会还原 A。"修改"类变更需要重新应用旧配置。
2. `no router ospf 100` 会删除整个进程,可能比预期影响更大。
3. 取反命令的**执行顺序**对依赖关系敏感(VRF、ACL、BGP 策略)。
4. "<3s"没有给出测量口径(仅 diff 计算?还是含 SSH 往返、分页、提交?)。
5. 回滚后"重新验证基线"失败时的行为未定义。

**建议**:
- 优先使用设备原生机制:IOS 的 `configure replace`、Junos 的 `rollback` / `commit confirmed`、EOS 的 config session / `configure replace`、IOS-XR/NX-OS 的原生回滚。diff 取反仅作为不支持事务的设备的降级路径。
- 增加"回滚安全等级"小节:哪些命令可自动反向,哪些必须人工确认。
- 对降级路径,规定按依赖关系倒序执行。
- 明确回滚失败的升级路径(自动升级到 Tier 2,还是标记人工介入)。
- 给出"<3s"的测试条件(设备类型、命令规模、网络延迟)。

#### P1-2 YAML 意图文件加 schema 与版本号

**问题**:§4 是示例而非规范。没有 `apiVersion`,没有类型/必填/默认值定义,v3.3 到 v4.0 之间必然演进,缺少版本字段会造成向后兼容问题。

**建议**:
- 在文件头加 `apiVersion: pnetgimini/v1alpha1`(及可选的 `kind`)。
- 附一份 JSON Schema 或字段表,明确类型、必填、枚举、默认值。
- 明确 `max_crc_errors_delta` 等"增量类"指标的采集窗口(需要基线计数器)。
- Python 实现上,可用 pydantic 建模并导出 JSON Schema,让代码成为 schema 的唯一来源。

#### P1-3 健康门断言的轮询与超时语义

**问题**:OSPF 邻居到达 FULL、BGP 到达 Established 都需要时间。一次性断言会产生误报。文档没有说明等待与重试策略。

**建议**:
- 为每类断言定义:轮询间隔、总超时、判定为失败的条件。
- 区分"尚未收敛"(继续等待)与"确定失败"(如配置错误导致的 Idle/Active 循环)。

#### P1-4 说明 asyncio 与 Netmiko 的结合方式

**问题**:文档主打"高并发 asyncio 协程引擎",同时使用 Netmiko(同步库,`terminal_server` 类型)。两者如何配合没有说明。另外 `terminal_server` 只是透传控制台流,登录、enable、分页都需要自行处理。

**建议**:
- 写明并发模型(线程池 `run_in_executor`,还是改用 scrapli / asyncssh 等异步库)以及并发上限。
- 说明控制台流场景下的登录、提权、分页处理策略。

#### P1-5 并发控制与幂等

**问题**:文档没有定义以下场景:
- 同一节点的并发操作如何串行化(锁粒度:节点级还是 lab 级)。
- 同一条链路被两个混沌测试同时挂起会怎样。
- config push 重试时如何避免重复下发。

**建议**:新增"并发控制与幂等"小节,明确锁模型、混沌测试互斥规则和重试的幂等键。

#### P1-6 `wait_console` 正则加锚定

**问题**:启动早期的 Banner 或 bootloader 日志里可能出现 `>` 或 `#`,提前命中示例正则 `([>#]|<.+>|Press RETURN)`。

**建议**:
- 正则增加行首/行尾或主机名上下文锚定。
- 命中后主动发送回车做二次确认。
- 注意:原文已强调 `wait_console` 只是事件探针而非就绪门,这条建议是对示例正则的收紧,而非对语义的修改。

### P2:完整性与安全细节

#### P2-1 定义 `AuditReport` 的 schema

文档多处提到"JSON + TXT 审计报告"、"回滚审计报告",但没有格式。v4.0 要接入 CI/CD,机器可读的稳定格式是前提。
**建议**:定义 JSON schema(至少包含 lab id、节点键、各 gate 结果、diff 摘要、混沌时间线、收敛测量值、最终状态),并说明归档位置。

#### P2-2 安全与凭据细节

- OOB 的 `ssh_config` 文件的权限与生命周期(临时文件?何时清理?)。
- `session_token`、agent 密码在内存中的驻留与清理。
- Tier 2 的 `stop → wipe → start`:`wipe` 的语义(仅 startup-config,还是整个磁盘)、是否需要显式确认(破坏性操作)。
- `MaskingFilter` 只解决日志脱敏,不等于凭据管理,文档应区分两者。

#### P2-3 契约表:谁发起、谁负责失败

建议加一张表,让开发者一眼看出"这件事归谁"。示例(请与实际实现核对后再采用):

| 需求 | 原语 / 机制 | 方向 | 失败归属 |
|---|---|---|---|
| 拓扑对账 | Git 推送 → EVE IaC reconcile | Git → EVE IaC | EVE IaC |
| 获取 OOB 入口 | `oob start` + inventory | PNet → EVE IaC | EVE IaC |
| 事件探针 | `wait_console` | PNet → EVE IaC | EVE IaC |
| 设备配置下发 | OOB SSH | PNet → 设备 | PNetGimini |
| OSPF/BGP 验证 | 遥测采集 + 断言 | 设备 → PNet | PNetGimini |
| 链路故障 | `set_link_suspend` | PNet → EVE IaC | EVE IaC |
| 丢包/抖动 | `apply_link_quality` | PNet → EVE IaC | EVE IaC |
| 设备配置回滚 | `ConfigDiffEngine` / 原生回滚 | PNet 内部 | PNetGimini |
| Tier 2 节点重置 / 全 lab 对账 | stop-wipe-start / `reconcile_project` | PNet → EVE IaC | EVE IaC |

#### P2-4 区分四类"回滚"

文档中"回滚"一词语义较宽。建议明确:
- **配置回滚**:设备内 running/startup config,归 PNetGimini。
- **场景回滚**:恢复链路、撤销损伤,经由 EVE IaC。
- **基础设施回滚**:拓扑/节点,归 EVE IaC。
- **验证**:只观察,不涉及回滚。

并写死一条规则:PNetGimini 不得绕过 EVE IaC 直接修改拓扑。

#### P2-5 混沌测量的精度边界

通过控制台会话测量毫秒级(如 1500 ms)收敛时间,受 ping 间隔、控制台/SSH 延迟、虚拟机调度抖动影响,阈值可能产生不稳定的结果。
**建议**:说明测量方法与精度范围,阈值设置要留余量,必要时提供重复运行取统计值的机制。

## 3. 评审中提出但**不建议采纳**的意见

| 意见 | 不采纳的理由 |
|---|---|
| "为老 IOS / ASA 的 Day-0 增加 Telnet 回退" | 文档的 OOB 代理直接连接节点控制台流,不依赖设备自身的 SSH 服务,Day-0 并不需要 Telnet 回退。该建议还把它挂在 `wait_console` 上,是对该原语语义的误读。 |
| "`apply_link_quality` 的 `loss` 单位不明" | 原文已写明是整数百分比(如 2)。需要补的是 `bandwidth` 等其他参数的单位。 |
| "PNetGimini 的验证结果可能反向修改期望状态,形成反馈环" | 在原文设计里,Git 同时拥有拓扑与运维意图,PNetGimini 只修改设备内部状态,没有明显的反馈路径。可在 P2-4 的规则里一并写死,但不必作为独立风险。 |
| "EVE-NG 在 1000 节点以上会成为瓶颈""v4.0 范围过大应拆成 v3.6–v3.8" | 无依据的推测,文档本身也未提供可核对的数据。 |
| 各类评分(8/10、9/10 等) | 没有评分标准,不具备可比性。 |
